# checklist.md (pytest 출제 검토 체크리스트 v2)

> 목적: "buggy 구현 다수 + golden 1개" 단위테스트 출제에서
> 수험자의 추측을 제거하고 채점 안정성을 확보하기 위해 결정점(Contract)을 고정한다.

---

## 0. 게이팅(출제 차단) 항목 — 발견 즉시 🔴 Critical

- [ ] Markdown 렌더링 오류 (코드블록 미닫힘, 표/리스트 깨짐)
- [ ] 입력/출력 계약이 모호하여 합리적 다른 구현이 가능한 상태
  - [ ] 허용/금지 입력이 불명확 (예: 공백/빈값/음수/None)
  - [ ] 예외 타입(또는 실패 정책)이 불명확
  - [ ] 반환 구조/필수 키가 불명확
- [ ] 구현 내부 강제(순서/알고리즘/자료구조) 문구 포함
- [ ] 예시가 규칙과 충돌
- [ ] 난이도-분량 심각 불일치 (예: Very Easy인데 40줄+ & 중복 다수)

---

## 1. 문제 목표/난이도 정합성

- [ ] 이 문제의 평가 역량이 1~2줄로 명확히 정의되어 있는가?
  - 예: 경계값, 구조 검증, 정규화, 파싱, 워크플로우
- [ ] 난이도와 요구 역량이 일치하는가?
  - Very Easy: 단일 규칙/단일 함수/명확한 입출력
  - Easy: 예외/경계값 조금 증가
  - Medium: 조합 규칙/정규화/다수 예외
  - Hard: 파이프라인/상태/복합 스펙

---

## 2. 입력 계약(Input Contract)

### 2-1. 타입
- [ ] 파라미터 타입이 정확히 명시되어 있는가?
- [ ] Python 특이 케이스 정책이 필요한가?
  - [ ] bool이 int로 취급되는 문제 처리(허용/금지)
  - [ ] None 허용 여부
  - [ ] float/Decimal 허용 여부

### 2-2. 값 범위/제약
- 숫자형
  - [ ] 최소/최대값(있다면) 명시
  - [ ] 음수 허용 여부
  - [ ] 0 처리 규칙
- 문자열
  - [ ] 빈 문자열/공백만 문자열 처리 규칙
  - [ ] strip 적용 여부 및 범위
  - [ ] 대소문자 처리(정규화/구분)

### 2-3. 구조 입력(dict/JSON 등)
- [ ] 필수 키/선택 키/기본값 명시
- [ ] 추가 키 허용/무시/에러 정책
- [ ] 키 대소문자 구분 여부
- [ ] 중첩 구조 검증 깊이(필요 시)

---

## 3. 출력 계약(Output Contract)

- [ ] 반환 타입이 명확한가? (list/dict/str 등)
- [ ] 반환 구조(필수 키/필드) 명시
- [ ] list 반환 시 순서 규칙
  - [ ] 입력 순서 유지? 정렬? 순서 무관?
- [ ] dict 반환 시 키 순서 강제 여부(대부분 강제하지 않음)
- [ ] 문자열 반환 시 포맷 규칙
  - [ ] 공백 포함 여부
  - [ ] 구분자/접미사 위치
  - [ ] 로케일/기호 고정 여부

---

## 4. 정규화(Normalization) 규칙

- [ ] 어떤 필드에 strip() 적용하는지 명시
- [ ] 빈 문자열 → None 변환 규칙(필요 시)
- [ ] 토큰 매핑은 허용 집합으로 열거(etc 금지)
- [ ] 대소문자 정규화 기준(lower/upper) 명시(필요 시)

---

## 5. 검증(Validation) 규칙

- [ ] 형식 검증 vs 의미 검증 범위가 명확한가?
  - 날짜: 형식만? 달력 유효성까지?
- [ ] 이메일/전화번호/ID 등 규칙이 모호하지 않은가?
  - 가능하면 “간단 규칙”을 문장으로 고정(또는 정규식)

---

## 6. 에러 처리 계약(Error Contract) — 최우선

### 6-1. 예외 타입
- [ ] 상황별 예외 타입이 고정되어 있는가?
  - 권장: 타입 오류 TypeError / 값·형식 오류 ValueError

### 6-2. 부분 성공 정책
- [ ] 입력 여러 건 처리 시:
  - [ ] 하나라도 실패하면 전체 실패?
  - [ ] 유효한 것만 반환?
  - 둘 중 하나를 반드시 명시

### 6-3. 다중 실패 우선순위(필요한 경우에만)
- [ ] 동시에 여러 조건이 실패할 때 우선순위가 필요한가?
  - 필요하면 “우선순위”를 스펙에 명시
  - 구현 내부 순서 강제와 혼동되지 않게 주의

### 6-4. 에러 메시지
- [ ] 메시지 exact match를 강제하지 않는가?
- [ ] 필요 시 키워드 포함 정도만 권장

---

## 7. 난이도별 분량/구조 점검

- [ ] 템플릿 구조 준수 (시그니처 → 규칙 → 예시 → 힌트)
- [ ] 중복 제거 완료
- [ ] Very Easy는 15~25줄 내로 압축되어 있는가?

---

## 8. 예시(Examples) 품질

- [ ] 정상 예시 최소 2개(대표 + 경계값)
- [ ] 실패 예시 최소 1~2개(핵심 실패 축)
- [ ] 예시가 스펙을 “결정”하도록 설계되어 있는가?
  - 공백 줄 무시 규칙이면 공백 줄 예시 포함 등

---

## 9. 문제 유형별 추가 체크

### 9-A. 수치 계산
- [ ] 0/음수/큰 값 경계
- [ ] 부동소수점이면 허용 오차/반올림 규칙 필수

### 9-B. 파싱(CSV/JSON/로그)
- [ ] 공백 줄 처리(헤더 전/후/중간)
- [ ] 줄바꿈(\n vs \r\n)
- [ ] 스키마(헤더) 규칙: 정확히 일치? 순서 고정? 대소문자?
- [ ] 따옴표/이스케이프 지원 범위(필요 시)

### 9-C. 워크플로우/파이프라인
- [ ] 단계 정의(순서)와 실패 시 중단 여부
- [ ] 롤백/정합성 규칙
- [ ] 입력 불변성(원본 객체 변경 금지)
- [ ] 멱등성/독립성(필요 시)

---

## 10. 버그풀(Buggy impl) 정합성 점검

- [ ] 버그 구현이 서로 다른 축을 깨도록 설계되었는가?
  - 타입/범위/정규화/구조/예외/경계값 등
- [ ] golden 구현이 스펙을 100% 준수하는가?
- [ ] 테스트가 스펙 밖의 것을 강제하지 않는가?
  - 메시지 exact match, dict 키 순서, 내부 처리 방식 등

---

## 11. 최종 자문 질문
> "이 스펙만 읽고 두 명이 구현하면, 모든 테스트 결과가 동일한가?"

- [ ] Yes가 아닐 경우: 1문장으로 결정점을 추가해 닫는다.
