# 시나리오 작성 가이드라인

> 뮤테이션 테스트 문제의 비즈니스 시나리오를 실감나게 작성하는 방법

---

## 핵심 원칙

### 1. 구체성 (Specificity)
추상적 설명 대신 구체적인 서비스, 상황, 숫자를 사용합니다.

| 추상적 (BAD) | 구체적 (GOOD) |
|-------------|--------------|
| 금융 앱 | 토스 송금, 카카오뱅크 이체 |
| 이커머스 | 쿠팡 장바구니, 마켓컬리 배송 |
| 플랫폼 | GitHub Actions, AWS Lambda |
| 오류 발생 | 1건당 500원 손실, 월 1000건 CS 인입 |

### 2. 사용자 관점 (User Perspective)
기술적 설명보다 사용자가 경험하는 상황을 묘사합니다.

```markdown
# BAD
"이 함수는 이메일 형식을 정규표현식으로 검증합니다."

# GOOD
"사용자가 회원가입 폼에 이메일을 입력하고 '다음' 버튼을 누르면
이 함수가 호출되어 입력값을 검증합니다."
```

### 3. 비즈니스 임팩트 (Business Impact)
버그가 발생했을 때 비즈니스에 미치는 영향을 정량화합니다.

```markdown
# BAD
"버그가 있으면 문제가 발생합니다."

# GOOD
"버그가 있으면 월 5000건의 정상 이메일이 거부되어
회원가입 전환율 3% 하락, 예상 매출 손실 월 1500만원"
```

## 도메인별 시나리오 템플릿

### fintech (금융)

#### 서비스 예시
- 토스, 카카오뱅크, 네이버페이, 뱅크샐러드
- 토스증권, 업비트, 빗썸 (투자/거래)

#### 시나리오 키워드
- 송금, 이체, 출금, 입금
- 한도, 수수료, 정산
- 본인인증, 보안, 감사

#### 위험 유형
| 위험 | 시나리오 | 피해 |
|------|---------|------|
| 자금 오류 | 이중 출금, 마이너스 잔액 | 직접적 금전 손실 |
| 규제 위반 | 한도 초과 이체 허용 | 금감원 제재, 과태료 |
| 정산 불일치 | 수수료 계산 오류 | 회계 감사 지적 |
| 보안 취약점 | 음수 금액 우회 | 해킹, 자금 탈취 |

#### 예시 시나리오
```markdown
당신은 **토스**의 QA 엔지니어입니다. `can_withdraw` 함수는 사용자가
"송금하기" 버튼을 누를 때 잔액 검증을 위해 호출됩니다.

매일 300만 건의 송금 요청에서 이 함수가 호출되며, 0.1%의 오류율만
발생해도 하루 3000건의 고객 컴플레인이 발생합니다.
```

### commerce (이커머스)

#### 서비스 예시
- 쿠팡, 마켓컬리, 배달의민족
- 네이버 스마트스토어, 무신사

#### 시나리오 키워드
- 장바구니, 결제, 배송비
- 할인, 쿠폰, 적립금
- 재고, 품절, 예약

#### 위험 유형
| 위험 | 시나리오 | 피해 |
|------|---------|------|
| 매출 손실 | 할인 과다 적용 | 마진 손실 |
| 고객 이탈 | 정상 할인 누락 | 결제 포기 |
| 재고 오류 | 품절 상품 판매 | 취소 처리, CS 비용 |
| 배송 지연 | 배송비 계산 오류 | 고객 불만 |

#### 예시 시나리오
```markdown
당신은 **쿠팡**의 결제 시스템 QA 엔지니어입니다. `calculate_cart_total`
함수는 "결제하기" 버튼 클릭 시 최종 금액을 계산합니다.

블랙프라이데이 기간에는 초당 1만 건의 결제가 발생하며,
1원의 계산 오류도 일일 8600만원의 정산 불일치로 이어집니다.
```

### platform (플랫폼)

#### 서비스 예시
- AWS, GCP, Azure (클라우드)
- GitHub, GitLab (개발 도구)
- Slack, Notion (협업 도구)

#### 시나리오 키워드
- 인증, 권한, 토큰
- API, 요청, 응답
- 스케줄링, 큐, 비동기

#### 위험 유형
| 위험 | 시나리오 | 피해 |
|------|---------|------|
| 인증 실패 | 유효 토큰 거부 | 서비스 이용 불가 |
| 권한 오류 | 무단 접근 허용 | 보안 사고 |
| 비결정성 | 시간 의존 버그 | 간헐적 장애 |
| 상태 누출 | 전역 상태 오염 | 테스트 불안정 |

#### 예시 시나리오
```markdown
당신은 **GitHub**의 QA 엔지니어입니다. `validate_jwt` 함수는 모든
API 요청의 인증 토큰을 검증합니다.

초당 100만 건의 API 요청이 이 함수를 통과하며,
1ms의 지연도 전체 시스템 응답 시간에 영향을 미칩니다.
```

### saas (SaaS)

#### 서비스 예시
- Notion, Figma, Canva (생산성)
- Salesforce, HubSpot (CRM)
- Stripe, PayPal (결제)

#### 시나리오 키워드
- 구독, 플랜, 요금제
- 멀티테넌시, 팀, 워크스페이스
- 입력 검증, 폼, 유효성

#### 위험 유형
| 위험 | 시나리오 | 피해 |
|------|---------|------|
| 데이터 유출 | 테넌트 격리 실패 | 보안 사고 |
| 과금 오류 | 구독 계산 버그 | 매출 손실/초과청구 |
| 입력 오류 | 잘못된 이메일 허용 | 발송 실패 |
| 협업 오류 | 권한 동기화 실패 | 작업 충돌 |

#### 예시 시나리오
```markdown
당신은 **Notion**의 QA 엔지니어입니다. `is_valid_email` 함수는
팀원 초대, 페이지 공유, 댓글 알림 등 모든 이메일 관련 기능에서 사용됩니다.

하루 50만 건의 이메일 발송 중 0.5%가 바운스되면
이메일 서비스 평판 점수 하락 및 스팸 분류 위험이 증가합니다.
```

### common (공통)

#### 특성
- 특정 도메인이 아닌 프로그래밍 공통 패턴
- 언어/프레임워크 특성에 집중

#### 시나리오 키워드
- 타입, 변환, 캐스팅
- 순회, 반복, 컬렉션
- 참조, 복사, 불변성

#### 위험 유형
| 위험 | 시나리오 | 피해 |
|------|---------|------|
| 런타임 오류 | 타입 불일치 | 서비스 크래시 |
| 데이터 손상 | 참조 공유 버그 | 예측 불가 동작 |
| 성능 저하 | 비효율적 순회 | 응답 지연 |
| 메모리 이슈 | 무한 루프 | 서버 다운 |

#### 예시 시나리오
```markdown
당신은 데이터 처리 파이프라인의 QA 엔지니어입니다. `filter_items` 함수는
대용량 리스트에서 조건에 맞는 항목을 필터링합니다.

Python에서 리스트 순회 중 수정은 흔한 실수이며,
이 버그는 조용히 잘못된 결과를 반환하여 발견이 어렵습니다.
```

## 버그 설명 작성법

### 버그 카테고리별 표현

| 카테고리 | 설명 표현 예시 |
|---------|--------------|
| 경계값 | "qty=10일 때 15% 대신 10% 적용 (off-by-one)" |
| 조합 오류 | "쿠폰 미달 + stackable=False 조합에서 VIP 할인 누락" |
| 예외 누락 | "음수 입력에 ValueError 대신 False 반환" |
| 상태 오류 | "동일 쿠폰 재사용 시 hidden state로 인한 거부" |
| 정책 위반 | "gift_card 포함해 min_subtotal 계산 (정책 위반)" |

### 좋은 bug_description 예시

```
# BAD - 너무 추상적
"경계값 오류가 있습니다."

# GOOD - 구체적
"수량 할인 경계값(3/5/10)에서 >= 대신 > 비교를 사용해
quantity가 정확히 3, 5, 10일 때 할인율이 한 단계 낮게 적용되는 off-by-one 버그."
```

## 위험성 테이블 작성법

### 구조
```markdown
| 위험 유형 | 발생 시나리오 | 예상 피해 |
|-----------|--------------|----------|
| [기술적 버그] | [사용자 경험 상황] | [정량적 비즈니스 피해] |
```

### 피해 정량화 예시

| 추상적 | 정량적 |
|-------|-------|
| 고객 불만 | 월 1000건 CS 인입, 처리 비용 500만원 |
| 매출 손실 | 건당 평균 5000원 × 일 100건 = 월 1500만원 |
| 서비스 장애 | 다운타임 1분당 매출 손실 100만원 |
| 보안 사고 | 개인정보 유출 시 과태료 최대 4억원 |

## 체크리스트

### 시나리오 품질
- [ ] 구체적인 서비스명 언급
- [ ] 사용자 관점의 상황 묘사
- [ ] 호출 빈도/규모 언급 (일 N건, 초당 N건)
- [ ] 오류율의 비즈니스 임팩트 정량화

### 위험성 테이블
- [ ] 3개 이상의 위험 유형
- [ ] 각 위험의 구체적 시나리오
- [ ] 정량적 피해 (금액, 건수, 시간)

### 버그 설명
- [ ] 어떤 입력에서 발생하는지 명시
- [ ] 예상 결과 vs 실제 결과
- [ ] 테스트 기법 키워드 포함 (boundary, equivalence 등)
